# Flight Tools

The scripts the acceptance flights are launched and read with. They are
evaluation tools: nothing here is built into the stack or run by a gate, and
none of them is a criterion (the mission check in
[`docs/testing.md`](../docs/testing.md) is). Run them from the repository
root on the host unless a line says "inside the container". What they write
(run logs, flags, series tables, recordings, replay binaries) goes to
`log/tools/`, which git ignores.

**A script a tracked document cites lives here, under git** (C++ built
against the package in `drone_city_nav/tools/`), with a line on this page:
a figure in a document has to be reproducible from the repository.
`log/tools/` holds drafts, data and what the tools write, never the code a
document points at; a draft that a document comes to cite moves here first
(the owner, 2026-10-13). `scripts/tests/test_tools_tracked.py` holds every
tool to a line on this page and to parsing.

`log/tools/` is pruned like every log (`scripts/prune_sim_logs.sh`, a week):
an entry directly inside it goes when nothing in it was touched for seven
days. A directory holding a `.keep` file at its top is never deleted, and
that is how anything worth more than a week is kept:

| Kept directory | What it holds |
|---|---|
| `log/tools/journal/` | the goal journals (`goal_journal_*.md`) and the series tables |
| `log/tools/diagnostics/` | one-off scripts and data of single investigations |
| `log/tools/vio/`, `log/tools/replay/` | recorded flights for the offline replay (r575, r576; r779, r795) and the replay binaries |
| `log/tools/truth25/`, `log/tools/proof_leak/`, `log/tools/texture/`, `log/tools/stereo/` | truth grids and measurement data the documents cite |
| `log/tools/part1/`, `log/tools/part2/` | the smoke-and-light goal: the smoke rig's levels (`final/`; the light's calibration in part 1's, the rest at the pair's final noise in part 2's) and the estimator's replays over the rig's records (`vio/`, their frames removed) the smoke documents cite |
| `log/tools/part3/`, `log/tools/part6/`, `log/tools/part8/`, `log/tools/part11/`, `log/tools/stall/`, `log/tools/trials/` | the technical-debt goal's and the owner's trials' drafts and data; the scripts the documents cite from them moved here (`blind_phase.py`, `k27_side.py`, `speed_limiters.py`, `airframe_size.py`, `drone_city_nav/tools/mppi_cpu_rollout_benchmark.cpp`) |

A loose file cannot be kept: check logs (`run_rNNN.log`), gate logs and
flags go after a week. A new recording or result that has to stay goes into
a kept directory, or into a new directory with its own `.keep`.

Runs are named `rNNN`; a flight's artifacts are in `log/runs/rNNN/` and its
mission check's output in `log/tools/run_rNNN.log`.

## Launching

| Tool | What it does | Use |
|---|---|---|
| `gates.sh` | The whole pre-commit gate in the dev container, detached: format, build, unit tests, script tests, quality; a C++ source that differs from HEAD is compiled by the gate whatever built it before, so that its warnings are in the gate's log. Verdict in `log/tools/gate_flag.txt` (`X=0` is green), output in `log/tools/gate_all.log`. `--docs`: for a change to Markdown files alone, the script tests only (the ones that read the documents), about a minute; refused with `X=1` when anything else differs from HEAD. `--replay`: the stack replayed on every bag kept under `log/tools/replay/regression/<run>/` (`replay_stack.sh`, the poses within 0.05 m at p95 of the flight's), `X=1` on a failed replay or no kept bag; about fifteen minutes for the two sets, after the whole gate on a change to the estimators, the obstacle memory or the planner's input path (the owner's decision of 2026-11-05). | `./tools/gates.sh`, then poll the flag; `./tools/gates.sh --docs` for a documentation-only commit; `./tools/gates.sh --replay` for the kept bags. Do not edit tracked files while it runs. |
| `series2.sh` | Acceptance flights one at a time on the current commit, on the flight's core set (`FLIGHT_CPUSET`, `0-13` of this host unless set; empty for the whole host; specification A4). Prunes logs older than a week, waits until the host has been quiet for 60 s, stops any simulation before and after, appends the check's key lines to `log/tools/journal/series_<commit>_<profile>.txt`. | `./tools/series2.sh r950 r951` (cameras); `./tools/series2.sh --lidar r954` (`--lidar` first); another scenario with `TARGET=sim-urban-light-lost-headless SMOKE_DURATION_S=400 ./tools/series2.sh r939`. |
| `host_verdict.py` | Whether a flight counts, by the host it was flown on (specification A7): `HOST valid` or `HOST VOID` with the reason, from the real-time factor at the median (0.82 on the stereo set, 0.97 on the lidar, of the factor the run asked for), the resource sampler's largest gap (2 s) and the age of the estimator's poses on their way to the autopilot (300 ms at the 95th percentile, and the oldest of any second past the estimator's first five reports). The series launcher appends it to the series table after every flight. | `python3 tools/host_verdict.py r981` |
| `rtf_watchdog.py` | Whether a flight is being flown under a load that will void it, read while it flies: the median of the simulator's real-time factor over the last 30 sampled seconds (after the flight has got going) against the verdict's floor of the factor the run asked for. `WATCHDOG ok`, `slow` (exit 1) or `waiting`. | `python3 tools/rtf_watchdog.py r1098 --lidar --factor 1.0` |
| `fly_until_valid.sh` | One flight that counts, on a host another task may load: a `series2.sh` flight watched every 20 s by the watchdog, stopped at once when slowed, judged by `host_verdict.py` after (a flight with no line of the mission check was cut and is void), and flown again under the next number when stopped or void, at most the stated number of times. A flight that counts is the result whatever its check says. `TARGET`, `SMOKE_DURATION_S` and `REAL_TIME_FACTOR` pass through. Lines in `log/tools/fly_until_valid.txt` (`VALID`, `VOID reason`, `WATCHDOG reason`), then `END`. | `./tools/fly_until_valid.sh --lidar 1130 4`; `TARGET=sim-urban-low-battery-headless SMOKE_DURATION_S=1800 ./tools/fly_until_valid.sh 1140 4` |
| `release_check.sh X.Y.Z [--published]` | Every place a release's version lives, read before the release commit ([`docs/release_process.md`](../docs/release_process.md) step 4): `package.xml`, the changelog section, the readme's current release, no roadmap item left "Not yet in a release", no specification row left unstamped, the evidence folder with its `.keep`, the tree clean on `main`, the tag absent; with `--published`, the tag on HEAD and on origin, the GitHub release page present with the changelog entry's text. One line a check, OK or FAIL. |
| `mx.sh` | One flight of roadmap item 17's acceptance matrix by line number (1 cameras, 2 lidar, 3 long failures, 4 light lost, 5 severe failure, 7 low battery, 8 goal outside). Refuses to start while a flight runs or the run exists; marks its end in `log/tools/mx_flag.txt`. | `./tools/mx.sh 5 r944 &` |
| `mxw.sh` | Waits up to 9.5 minutes for that flight; prints `DONE` or `RUNNING`. Never stops a flight. | `./tools/mxw.sh r944` |

Flights run strictly one at a time. A flight `host_verdict.py` calls void is
flown again, and a crash in it is not a defect. On a host that another task
loads from time to time, every flight goes through `fly_until_valid.sh` or
`record_until_pass.sh`: the load is noticed while the flight flies, the flight
is stopped, and it is flown again when the host is quiet; the foreign
processes are never touched (specification A4).

A recorded flight the host's verdict counts is a flight like any other
(specification A11); a row that says `HOST VOID` is a demonstration. Lidar
flights are not recorded: the location is dark and the lidar carries no
light, so the world half of the picture shows nothing. A slowed flight of
any kind is `REAL_TIME_FACTOR=0.5 ./tools/series2.sh r1100`.

## Replaying The Lidar-Inertial Estimator Offline (`lio/`)

A lidar flight's scans and the autopilot's IMU recorded as a rosbag inside the
simulation container, extracted once, and replayed through the repository's
lidar-inertial estimator with no simulator; a change of that estimator is
measured on the record before any flight (roadmap item 13 set its thresholds
this way). The record lands under `log/tools/replay/RUN/`, a directory kept by
its `.keep`.

| Tool | What it does | Use |
|---|---|---|
| `lio/record_flight.sh` | One flight on the lidar profile through `fly_until_valid.sh` (one attempt) with `ros2 bag record` of `/lidar_3d/points`, the IMU, the autopilot's attitude and the barometer attached inside the container, then the extraction. | `./tools/lio/record_flight.sh r1230` |
| `lio/extract_bag.py` | The bag's scans (body FRD, the extrinsic of `urban_mvp.yaml` applied) to `scans.bin`, the IMU to `imu.csv`, the attitude to `attitude.csv` and the barometer to `baro.csv`, record by record, so a bag cut off without its footer still yields its data. | inside the container, called by `record_flight.sh` |
| `lio/build_replay.sh`, `lio/replay_lio.cpp` | Builds the replay against the tree's localization library (after `make build`) and runs the estimator over a record; options are `key=value` overrides of the estimator's configuration (`corr`, `recovery`, `keyframes`, `range`, `tiltshare`, `heightshare`, ...), `lag` in ms, `out`, and the outside measurements of K45: `attitude=` (the record's attitude.csv) or `truth=` (the flight's gz_pose.csv) as the level, `baro=` (the record's baro.csv) as the height, `misalign=DEG` an IMU mount error to seed a tilted map. Writes the trajectory (with the estimate's roll and pitch) and the registration times. | `./tools/lio/build_replay.sh`, then inside the container `log/tools/replay/replay_lio log/tools/replay/r1230 HEADING out=log/tools/replay/r1230/base.csv` |
| `lio/replay_error.py` | A replay's (or the flight's own `lio_estimate.csv`'s) vertical error, horizontal error and tilt against the flight's truth, the rest's offset as zero, with marks every 15 s (`log/tools/lidar_speed/part4_r2145_heightshare.txt`). | `python3 tools/lio/replay_error.py r2145 log/tools/replay/r2145/replay_hs0.02.csv` |
| `lio/lio_cost.py` | The lidar-inertial estimator's cost in flight from its once-a-second line: `scan_ms` at p50, p95 and most, the scans let go (specification K23), the pose age's 95th percentile (A7). | `python3 tools/lio/lio_cost.py r1410 r1411` |
| `lio/rosbag1_to_record.py` | A real lidar-inertial recording in a ROS 1 bag (NTU VIRAL: an Ouster OS1-16 and a VN-100) as the replay's record through the rosbags library: scans.bin and imu.csv in the body frame (the lidar's extrinsic applied), gz_pose.csv from the Leica prism; `stampshift=` moves every sweep's stamp (0.05: the sweep's middle, roadmap item 25's one probe). | `/data/gazebo/venv/bin/python -I tools/lio/rosbag1_to_record.py BAG OUT truth=GT.csv flu=0 stampshift=0.05` |
| `lio/fastlio_record.sh`, `lio/fastlio_ntu_viral.yaml` | FAST-LIO (the tool image) over the converted recording (rosbags-convert of the bag), its /Odometry recorded to a CSV; the configuration for NTU VIRAL's horizontal lidar. | `./tools/lio/fastlio_record.sh /data/gazebo/datasets/ntu_viral/eee_01_ros2 OUT.csv 1.0` |
| `lio/record_report.py` | A lidar-inertial estimate over a real recording (ours, or FAST-LIO's odometry) against the recording's prism truth through `vio/euroc_report.py`: ATE, RTE over 10 m, the end. | `python3 -I tools/lio/record_report.py RECORD/gz_pose.csv RECORD/replay.csv kind=lio first_imu_ns=N out=report.csv` |
| `lio/compare.py` | Horizontal error of a replay against the flight's truth, the mission check's own measurement, in ten-second windows. | `python3 tools/lio/compare.py log/runs/r1230 log/tools/replay/r1230/base.csv` |

The heading argument is the vehicle's initial heading in NED radians (the
`initial_heading_rad` the flight ran with).

One-off diagnostics written for a single investigation stay in
`log/tools/diagnostics/` and are not tracked, as long as no document cites
them; the goal journals in `log/tools/journal/` say which was used for what.

The stereo pair's depth accuracy (specification K7) is built with the
package: `build/drone_city_nav/stereo_depth_accuracy DIR` inside the
container matches a gained record as the depth node does
(`drone_city_nav/tools/stereo_depth_accuracy.cpp`, its noise mask a copy of
the node's) and holds it against the evaluation depth camera.

The CPU rollout benchmark (roadmap item 28) is built with the package:
`build/drone_city_nav/mppi_cpu_rollout_benchmark` inside the container
prints what one MPPI rollout costs on a CPU core, in open space and in a
corridor.
